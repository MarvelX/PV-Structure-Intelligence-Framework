# WaterBase Mount Design

**Topic:** 面向水厂既有构筑物场景、支持多区域标准适配的分布式光伏支架产品方案与预选型 Demo

**Goal:** 设计一套用于面试展示的产品化作品，既能体现候选人的结构工程能力，也能体现制造业产品经理所需的场景抽象、标准化边界判断、国际化适配意识与数字化工具思维。

**Target Company Context:** 清源股份公开业务覆盖分布式支架、地面支架、跟踪器与数字化工具，具备较强海外市场属性。作品应贴近其“标准化支架 + 国际化适配 + 数字化支撑”的方向，而不是停留在单项目工程汇报。

---

## 1. Design Positioning

这套作品不定位为完整商业产品，也不定位为单项目案例复盘，而是：

`产品经理候选人的高质量场景化产品提案 + 半技术型预选型工具原型`

同时，这套作品也被定义为一套可复用的个人知识资产雏形，而不只是一次性的面试材料。

核心定位：

- 把既有水厂/污水厂构筑物上的分布式光伏支架经验，上升为可复制的产品方案。
- 用产品架构、标准化边界和多区域标准适配，体现产品经理思维。
- 用一个轻量网页 Demo，把经验进一步沉淀为前线可用的工具逻辑。
- 用方法论底稿、证据库和工具层，证明这不是临时拼接的表达，而是一套可以继续扩展的框架。

## 3. Product Concept

### 3.1 Product Name

`WaterBase Mount`

### 3.2 Subtitle

`面向水厂既有构筑物场景的多标准适配型分布式光伏支架解决方案`

英文副标题可用于封面或 Demo：

`A Multi-Standard Ready PV Mounting Solution for Water Infrastructure`

### 3.3 Core Value

WaterBase Mount 不是通用屋顶支架，而是清源现有分布式支架体系的一个高门槛场景扩展模块。它通过“共用平台 + 场景适配 + 标准适配 + 交付支持”的方式，把水厂构筑物场景中的复杂工程约束，转化为前线可理解、可筛选、可推广的产品逻辑。

## 5. Underlying Asset Layers

为了让这套作品既能面试展示、又能继续扩展，建议把资产分成四层：

### 5.1 Methodology Core

这是整个框架的底层引擎，用来支撑所有外显表达。

建议包含：

- 场景逻辑表：把跨度、风环境、腐蚀、干扰、运维等输入变量与推荐路径、风险等级、标准化等级对应起来
- 多区域标准适配矩阵：梳理中国、欧洲、美国、澳洲、日本等市场的适配要点
- 风险分类库：结构风险、运维风险、施工风险、合规风险、资料输出风险

这些内容可以作为内部工作底稿存在，不一定全部直接出现在面试主材料里，但必须支撑主材料。

### 5.2 Evidence Case Library

这部分用于证明框架来自真实项目，不是凭空概念化。

建议包含：

- 南昌/厦门等光伏支架相关项目的映射摘要
- 方案比选记录的抽象版
- 降本、风险前置、运维冲突解决等代表性案例
- 小论文、总结汇报、标准化沉淀的节选或摘要

### 5.3 Presentation Views

这部分用于支撑后续“一套底层，两套外壳”的输出方式。

当前阶段先保留：

- 清源视角：偏产品化、标准化、客户前端支持
- 宁德时代视角：偏技术评审、设计控制、项目风险闭环

### 5.4 Tooling Layer

这部分对应最终 Demo。

原则：

- 不是结构分析软件
- 不是复杂报价系统
- 是一款面向决策引导的轻量工具

## 6. Main Deck Structure

建议主方案册控制在 10 页左右。

### Page 1: Product Cover

- 标题：WaterBase Mount
- 副标题：面向水厂既有构筑物场景的多标准适配型分布式光伏支架解决方案
- 一句话定位：清源分布式支架体系下的特殊工业场景扩展模块

### Page 2: Why This Scenario

- 水厂具备稳定负荷与自发自用价值
- 既有构筑物空间可利用
- 常规工商业屋顶方案覆盖不足
- 高门槛场景值得通过产品化沉淀形成差异化

### Page 3: Translate Engineering Pain Points into Product Problems

- 承载能力不确定 -> 需要前置适配判断
- 管线/设备冲突多 -> 需要模块化布置逻辑
- 风/腐蚀/潮湿环境复杂 -> 需要分级材料与防腐策略
- 施工扰动受限 -> 需要低干扰安装路径
- 运维要求高 -> 需要检修友好的布局
- 区域标准差异 -> 需要标准适配框架

### Page 4: Product Goals and Design Principles

- 安全与耐久守底线
- 尽量标准化，减少非标
- 安装快，少扰动
- 运维友好
- 成本可控
- 平台化设计，支持多区域标准适配

### Page 5: Product Architecture

四层架构：

1. 共用结构平台层
2. 场景适配层
3. 标准适配层
4. 交付支持层

### Page 6: Standardization Boundary

三类边界：

- 标准产品
- 参数化产品
- 非标评审

### Page 7: Multi-Standard / International Adaptation

建议区域：

- 中国
- 欧洲
- 美国
- 澳洲
- 日本

建议字段：

- 区域市场
- 标准/认证语境
- 重点关注项
- 对产品的影响
- 输出资料要求

### Page 8: Scenario Selection and Solution Comparison

- 刚性支架适用边界
- 柔性支架适用边界
- 材料路线建议
- 基础与落柱逻辑
- 谨慎推进或不建议做的条件

### Page 9: Commercial and Delivery Value

- 提高前线识别效率

## 8. Demo Scope

Demo 定位：

`半技术型预选型工具`

不是工程精算软件，也不是纯展示网页。它应该表现为一款服务于销售、售前、产品和技术团队的场景预判工具。

它的灵魂不在于做复杂力学计算，而在于做 `决策引导`：

- 帮助前线快速识别推荐路径
- 帮助产品或技术团队判断边界与风险
- 帮助面试官看到候选人有把经验沉淀成规则与工具的能力

### 7.1 Inputs

- 构筑物类型
- 是否既有构筑物改造
- 跨度/高度等级
- 周边管线/设备干扰等级
- 运维通道要求
- 腐蚀环境等级
- 风环境等级
- 是否允许池壁落柱/外侧落柱
- 目标市场 / 标准体系

### 7.2 Outputs

- 推荐支架路径：刚性 / 柔性 / 需专项比选
- 标准化等级：标准 / 参数化 / 非标
- 材料方向建议
- 基础接口建议
- 风险提示
- 区域适配提醒
- 自动生成的方案摘要

### 7.3 Demo Home Layout

推荐结构：

- 顶部：工具标题和一句话定位
- 左侧：输入区
- 右侧：推荐结果区
- 底部：推荐理由摘要

设计风格：

- 工程理性
- 工具感
- 清晰、轻量
- 不做炫技式网页

## 9. Evidence and Retrospective Mapping

这套作品不能只展示“我做过什么”，还应展示“我现在如何用更高一层的方法重新理解过去的项目”。

建议明确加入一个工作原则：

- 用当前框架回看过去的南昌/厦门等项目
- 识别当年哪些风险可以更早发现
- 识别哪些方案其实可以更标准化
- 识别哪些经验适合沉淀进规则表和工具层

这部分的价值在于：

- 体现候选人不是停留在经验堆积，而是在持续升维
- 体现候选人具备“复盘 -> 抽象 -> 标准化”的能力
- 让战果库不只是存档，而成为框架真实有效性的证明

## 12. Success Criteria

面试官看完后，应形成以下印象：

1. 候选人不只是讲单项目，而是在做场景化产品抽象。
2. 候选人对结构和工程约束理解扎实。
3. 候选人理解标准化、参数化和非标边界。
4. 候选人理解国际化公司需要多区域标准适配。
5. 候选人具备把经验进一步做成工具的数字化思维。
6. 候选人正在把个人经验沉淀成一套可复用的方法论资产。

## 13. Risks and Mitigations

### Risk: Too much like engineering report

Mitigation:

- 减少计算细节
- 强化产品原则、边界、交付价值

### Risk: Too much like internet PM deck

Mitigation:

- 保留真实场景约束
- 保留支架路径与工程判断逻辑

### Risk: Demo overwhelms the story

Mitigation:

- Demo 只服务于产品逻辑演示
- 不做复杂算法或过度工程化
- 强化“决策引导”而不是“计算替代”

### Risk: International angle feels forced

Mitigation:

- 只讲平台化设计和区域适配逻辑
- 不堆砌规范条文

### Risk: Framework sounds abstract without proof

Mitigation:

- 用真实项目做映射
- 用复盘式总结证明框架有效
- 保留案例与证据库作为支撑

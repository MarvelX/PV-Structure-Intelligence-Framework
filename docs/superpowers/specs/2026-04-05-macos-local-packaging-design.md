# macOS Local Packaging Design

## 1. Goal

把当前 `V1 Working Tool` 从开发态的“命令行启动前后端”，推进到一个可以在 `macOS` 上双击运行的最小可交付形态。

这一轮的目标不是把产品做成完整桌面应用，也不是马上支持多平台安装，而是先解决最核心的交付问题：

`业务用户双击应用 -> 本地服务自动启动 -> 默认浏览器自动打开 -> 应用可直接使用`

这轮设计必须满足两个原则：

- 不要求用户手动打开终端或输入命令
- 不给后续 `Windows` 支持制造结构性障碍

## 2. Scope

### In Scope

- 仅支持 `macOS`
- 产出一个可双击运行的 `.app`
- 前端改为生产态静态构建
- 后端在生产态托管前端静态文件
- 引入一个 Python 启动器作为唯一入口
- 启动时自动执行本地数据库迁移
- 自动打开默认浏览器访问本地地址
- 运行时数据写入用户目录，而不是应用包内部
- 启动失败时给出明确错误提示

### Out Of Scope

- Windows 安装包
- Electron / Tauri
- 自动更新
- 代码签名与 notarization
- 托盘、菜单栏、原生窗口
- 多实例协调
- 远程发布、云端同步

## 3. Product Form

本轮交付形态定义为：

`macOS 双击启动器 + 本地 HTTP 服务 + 默认浏览器前端`

也就是说，应用对用户看起来像一个桌面 App，但真实运行方式仍然是本地单机 Web App。  
浏览器是显示层，Python 启动器是进程管理层，FastAPI 是唯一服务入口。

这样做的原因：

- 改动量远小于直接引入桌面壳框架
- 可以复用当前 React + FastAPI + SQLite 架构
- 生产态只需要维护一个本地服务进程
- 后续迁移到 Windows 时，启动器逻辑可以继续复用

## 4. Architecture

### 4.1 Production Runtime

生产态不再使用 `vite dev server`。

运行结构改为：

- 前端执行 build，产出静态文件
- FastAPI 挂载前端静态目录
- `/api/*` 继续提供 JSON API
- 非 API 路由回退到 `index.html`

因此，生产态只暴露一个本地端口。

### 4.2 Launcher

新增一个 Python 启动器，作为应用的唯一入口。

启动器职责：

- 解析应用资源目录
- 解析用户运行目录
- 初始化 runtime / exports 目录
- 执行 Alembic 迁移
- 启动本地 FastAPI 服务
- 轮询健康检查
- 服务就绪后自动打开浏览器
- 在退出时清理子进程

启动器不负责业务判断，不直接操作记录，不复制前端逻辑。  
它只是交付层和运行时协调层。

### 4.3 Data Paths

应用包本身必须视为只读资源区。

用户数据写入：

- `~/Library/Application Support/PV Structure Intelligence Framework/`

目录建议至少包含：

- `runtime/working_tool.sqlite3`
- `runtime/exports/`
- 可选日志目录

静态资产与前端 build 结果放在应用包资源目录中，只读使用。

## 5. Build Strategy

### 5.1 Build Pipeline

打包命令的顺序固定为：

1. 构建前端静态文件
2. 准备后端依赖与启动器入口
3. 用 `PyInstaller` 生成 macOS 图形化启动产物
4. 组装应用资源目录
5. 产出最终 `.app`

### 5.2 Packaging Choice

本轮选用 `PyInstaller`，而不是 AppleScript 壳或 Tauri。

原因：

- 比纯脚本壳更稳定，能做真正的进程托管和错误处理
- 比 Tauri 轻，能更快形成可交付产物
- 后续如果支持 Windows，可以沿用同一套启动器逻辑

### 5.3 Root Commands

建议新增：

- `npm run build:web`
- `npm run package:macos`
- 如有必要，增加 `npm run smoke:prod`

`package:macos` 必须是一个完整命令，不要求用户手动串联子步骤。

## 6. Startup Flow

双击 `.app` 后的标准流程：

1. 启动器启动
2. 定位应用资源目录
3. 检查用户运行目录，不存在则创建
4. 执行数据库迁移
5. 选择固定本地端口，若冲突则报错退出
6. 启动 FastAPI 生产服务
7. 轮询健康检查
8. 成功后调用系统 `open` 打开默认浏览器
9. 用户通过浏览器使用工具

退出策略：

- 启动器退出时，必须清理 FastAPI 子进程
- 浏览器页面关闭不自动终止服务
- 启动失败必须显示可读错误，而不是静默无响应

## 7. Error Handling

本轮至少需要覆盖以下启动错误：

- 本地端口被占用
- 数据库迁移失败
- 静态资源目录缺失
- API 服务未能在超时窗口内启动
- 用户目录不可写

错误提示的优先级是“可理解”，不是“技术完美”。  
第一版允许提示文本比较直接，但不能只输出栈追踪或静默失败。

## 8. UX Expectations

用户成功路径应为：

1. 双击 `.app`
2. 等待数秒
3. 浏览器自动打开首页
4. 正常进入两个 workspace
5. 完成 `Evaluate -> Save -> Fetch -> Export`

这一轮不追求“像原生桌面应用一样无浏览器感”，只追求“业务用户不需要命令行也能稳定使用”。

## 9. Implementation Boundaries

为了控制风险，本轮不同时做以下事情：

- 不重写前端为原生桌面窗口
- 不同时引入 Windows 打包
- 不做安装器、卸载器、签名、公证
- 不做复杂日志收集平台
- 不改动核心业务流程和规则资产结构

如需继续扩展，应在这轮交付稳定后再新增：

- Windows 打包
- 冲突后自动刷新与合并
- 更完整的启动器日志与诊断
- 真正桌面壳框架

## 10. Acceptance Criteria

本轮完成的标准是：

1. 在一台 macOS 机器上执行一次打包命令后，能够生成一个 `.app`
2. 双击 `.app` 后，无需终端命令即可自动打开浏览器
3. 首页、两个 workspace、记录保存、记录回看、导出都可正常使用
4. SQLite、导出文件等运行时数据写入用户目录，而不是应用包
5. 启动失败时，用户能看到明确错误提示

## 11. Recommended Implementation Order

建议实施顺序：

1. 先实现生产态 FastAPI 托管前端静态文件
2. 再实现 Python 启动器与健康检查
3. 再补 macOS 打包脚本和资源组装
4. 最后做双击启动冒烟测试

这样分阶段的原因是：

- 可以先在源码态验证生产运行模型
- 启动器问题和打包问题可以分开排查
- 最终 `.app` 只是在已验证运行模型外面再包一层

## 12. Risks

本轮最主要的风险有：

- `PyInstaller` 对资源路径和依赖收集不完整
- 前端 build 与 FastAPI 静态回退路由不一致
- 用户目录权限或端口冲突导致启动失败
- `.app` 产物在未签名情况下被系统额外拦截

这些风险都应通过“源码态生产运行验证 + 打包后真实双击冒烟”来尽早暴露，而不是等到最后统一处理。
